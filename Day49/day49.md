# Personal AI Playbook — #60DayClaudeChallenge Submission

**Task:** Build Personal AI Playbook (Turn Your Own AI Habits Into Reusable Workflow Systems)

This repo documents the full build: the prompt used to generate the app, the interview that personalized it, the shipped HTML tool, and a real test of its **Loop Builder** - using it to autonomously develop and validate an LLM-as-a-Judge evaluation prompt for a RAG pipeline.

---

## 1. What I Built

A single self-contained HTML file — **Personal AI Playbook** (`personal-ai-playbook.html`) with no external libraries, containing:

- **Dashboard** : overview, plain-language explainer, favorites, recent workflows
- **Workflows** : 12 personalized, reusable prompt templates across 6 categories, with `{{variable}}` fill-in fields, one-click copy, favorite/search/filter/duplicate/edit, saved to `localStorage`
- **Prompt Builder** : assembles one-shot prompts from 9 labeled building blocks (Role, Objective, Context, Constraints, Reasoning Strategy, Output Format, Tone, Examples, Quality Checks) with a live compiled preview
- **Loop Builder** : converts any prompt into an autonomous, self-evaluating loop (Goal, Evaluation Criteria, Improvement Strategy, Stop Conditions, Safety Rules)
- **Settings** : dark/light theme, default model, JSON import/export, keyboard shortcuts, reset

The tool was **not built generically** but was shaped entirely by a one-question-at-a-time interview before any code was written.

## 3. The Interview (Personalization Step)

Before writing any code, Claude asked these questions one at a time, mostly as multiple-choice:

| # | Question | My Answer |
|---|----------|-----------|
| 1 | Primary profession or role | **Software / technical (engineer, data, IT)** |
| 2 | Which parts of your work do you currently use AI for most? | **Writing/reviewing code & debugging, Learning new tools/frameworks & research, Automating repetitive scripts/data tasks, Planning/architecture & design decisions** |
| 3 | Biggest productivity bottleneck | **Switching context between tools/tasks kills focus** |
| 4 | Prompting experience level | **Advanced — structured systems, chaining, etc.** |
| 5 | AI models used most | **Mix of Claude + ChatGPT + others** |
| 6 | What outcome matters most from this Playbook? | **Autonomous/looping prompts + a Prompt Builder system** |
| 7 | Which tasks are truly daily/repetitive? | **Debugging, Code review & refactoring, Architecture/design planning docs, Data/script automation, Learning a new framework** |

**Direct effect on the build:** because the #1 bottleneck was *context-switching between AI tools*, Claude added a category that wasn't in the original spec's examples at all — **"Context Handoff"** — with two workflows ("Context Capsule for Tool Switch" and "Session Handoff Summary") specifically for carrying state between Claude, ChatGPT, and other tools.

## 7. Stress-Testing the Loop Builder

To validate that the Loop Builder produces genuinely usable autonomous prompts (not just a nicely formatted template), I compiled a real loop and ran it as a task in a separate chat:

**Loop compiled by the tool** (Base Task + Goal + Evaluation Criteria + Improvement Strategy + Stop Conditions + Safety Rules):

> Write an "LLM-as-a-Judge" evaluation prompt for a RAG pipeline, scoring **Contextual Faithfulness** (hallucination detection), outputting strict JSON `{"score": 1-5, "reasoning": "...", "hallucinated_spans": []}`. Simulate 3 test cases (perfectly faithful / subtle hallucination mixing real facts with fake numbers / answer that ignores context) and iterate the Judge prompt until it catches the subtle hallucination with zero false positives and 100% valid JSON — stopping when all criteria are met, no improvement for 2 iterations, or 5 iterations max. Safety rules: never delete/overwrite without confirmation, stop and report if stuck, never fabricate test results.

**Result:** 📄 [`rag_judge_prompt.md`](./rag_judge_prompt.md)

The loop worked as designed — it didn't stop at a plausible-looking first draft. It genuinely iterated on the hardest failure mode of LLM judges:

- **v1 → v2:** added an explicit, repeated **NUMBER MATCHING** rule after the initial draft under-caught a single swapped digit (`10.5M → 14.2M`) — LLM judges default to treating close numbers as "paraphrasing" unless told otherwise.
- **v2 → v3:** added a **CONTEXT SUBSTITUTION** rule after the off-topic test case scored higher than it should have, because "plausible but ungrounded" answers weren't explicitly forced to score 1.
- Final version passed all 3 test cases (TC1: score 5 / TC2: score 2–3 with the fabricated number flagged / TC3: score 1) with 100% valid JSON.

This is the clearest evidence that "loop building blocks" aren't cosmetic — **Stop Conditions + Evaluation Criteria** produced an actual second and third revision that fixed real, predictable LLM-judge failure modes.

## 8. Key Learnings

**1. Modular prompt design compounds — one-off prompts don't.**
Building 9 independent blocks (Role, Objective, Context, Constraints, Reasoning Strategy, Output Format, Tone, Examples, Quality Checks) instead of a fixed template means the same system produces a debugging prompt, a code review prompt, or an architecture prompt just by swapping which blocks are present. The reusable unit is the *block*, not the *prompt*.

**2. A loop is only as good as its Stop Conditions and Evaluation Criteria — not its Goal.**
The RAG-judge test proved this directly: the goal ("catch hallucinations") was clear from v1. What actually produced better prompts across iterations was forcing a concrete, checkable **Evaluation Criteria** (does it catch the specific swapped number?) paired with an **Improvement Strategy** ("fix one failing check at a time"). Without that pairing, a loop just repeats the same draft with different wording.

**3. Personalization from an interview beats personalization from a description.**
Asking one MCQ at a time surfaced a bottleneck (tool-switching) I wouldn't have thought to describe upfront — and it became its own category (Context Handoff) in the final product. Structured elicitation finds requirements that open-ended prompts miss.

**4. Self-explanatory UX is a design constraint, not a nice-to-have.**
Every building block needed a visible "what it does / why it matters" — both in the picker and once added — because a block like "Reasoning Strategy" is meaningless without that context. Designing for a first-time viewer (persistent explainer + permanent "What is this?" button, not just a one-time onboarding modal) forced clearer naming throughout the whole app, not just the help screen.
