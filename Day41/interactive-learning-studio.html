Module 1 · Foundational

LLM Foundations: Tokens, Embeddings & Attention

Before you can discuss RAG or agents credibly, you need the substrate underneath every GenAI system: how raw text becomes numbers, and how a transformer decides what to pay attention to.

1.1 From text to tokens

A language model never sees words. Text is first broken into tokens — sub-word chunks produced by an algorithm like Byte-Pair Encoding (BPE) or SentencePiece. "unbelievable" might become ["un", "believ", "able"]. Common words often stay whole; rare words get split into smaller, more frequent pieces. This is why LLMs are famously bad at counting letters — they often never see individual letters at all, only token IDs.

Analogy
Tokenization is like a chef pre-chopping ingredients into a fixed set of standard pieces before cooking. The chef (model) never sees "a whole onion" — only a fixed vocabulary of chopped pieces it has learned to combine.

1.2 Embeddings: meaning as geometry

Each token ID is mapped to a dense vector — an embedding — typically hundreds or thousands of numbers. Vectors that are geometrically close encode similar meaning. This is why king - man + woman ≈ queen works in embedding space: relationships become directions.

1.3 Self-attention: the transformer's core trick

For every token, self-attention computes a query, key, and value vector. The query of one token is compared against the keys of all other tokens to produce attention weights — how much each other token should contribute to this token's new representation. Stack this across many "heads" and many layers, and the model builds increasingly abstract representations of context.

Analogy
Imagine a crowded party where everyone is talking (the sentence's tokens). Self-attention is you deciding, moment to moment, whose voice to focus on to understand what's being said — and that focus changes depending on what word you're currently trying to interpret.

Core ML refresher, tied to LLMs

Loss & training

LLMs are pretrained with next-token prediction using cross-entropy loss: minimize the negative log-probability the model assigns to the true next token, across a massive corpus.

Overfitting, at scale

With web-scale data, classic overfitting is rarer than in small datasets — the bigger risk is memorization of exact training snippets and distribution shift at inference time.

Common misconception
"A bigger model is always a smarter model." In reality, data quality, training recipe (RLHF, instruction tuning), and context length management often matter more than raw parameter count for a given task.
Common misconception
"Temperature controls how 'creative' or 'emotional' the model feels." Temperature only rescales the probability distribution before sampling — it's a math knob on randomness, not a mood setting.
Key takeaways
  • Tokenization turns text into sub-word units before any math happens
  • Embeddings encode meaning as position/direction in high-dimensional space
  • Self-attention lets every token dynamically weight every other token
  • Pretraining objective is simply next-token prediction via cross-entropy loss
  • Model size is one lever among many — data and tuning matter just as much

Module 2 · Applied

Prompting, RAG & Fine-tuning

This is where interviews get practical: given a business problem, which lever do you pull — a better prompt, retrieval, or fine-tuning — and why?

2.1 Prompt engineering techniques

Zero-shot: ask directly. Few-shot: show 2-5 examples of input→output before the real task. Chain-of-thought: ask the model to reason step by step before answering, which measurably improves performance on multi-step problems. Role/system prompting: set persistent behavior via a system message separate from user turns.

Build a few-shot prompt

Task: classify support tickets as Billing, Bug, or Feature Request. Pick the option that best completes a strong few-shot prompt.

2.2 Retrieval-Augmented Generation (RAG)

RAG grounds generation in external, up-to-date knowledge without retraining the model. A query is embedded, matched against a vector database of document chunks via similarity search, and the top matches are inserted into the prompt as context before generation.

Analogy
Fine-tuning is a closed-book exam — the model must have memorized the facts beforehand. RAG is an open-book exam — the model can look things up in real time, so its "knowledge" stays current without re-studying.

Prompting vs RAG vs Fine-tuning

DimensionPromptingRAGFine-tuning
Time to implementMinutesDaysWeeks
Adds new factual knowledgeNoYes, dynamicallyYes, but static & costly to update
Best forFormat/tone/style controlUp-to-date or proprietary factsNew skills, tone at scale, latency-critical distillation
Hallucination riskHigher on unfamiliar factsLower, but retrieval errors possibleCan still hallucinate confidently
Common misconception
"RAG eliminates hallucination." RAG reduces it by grounding answers in retrieved text, but the model can still misread, mix, or ignore the retrieved context — retrieval quality and prompt design still matter enormously.
Common misconception
"Fine-tuning is how you teach a model new facts reliably." Fine-tuning is better at teaching style, format, and task behavior; it's a weak and expensive way to inject precise, verifiable facts compared to retrieval.
Key takeaways
  • Few-shot examples anchor output format far better than instructions alone
  • Chain-of-thought prompting helps most on multi-step reasoning tasks
  • RAG = open-book; fine-tuning = closed-book; pick based on how fresh facts need to be
  • Vector similarity search is the retrieval backbone of RAG
  • None of these three fully eliminates hallucination on their own

Module 3 · Advanced

Agentic AI: Loops, Tools & Memory

Agents turn an LLM from a one-shot text generator into a system that plans, acts on the world through tools, and iterates. This is the fastest-growing interview topic in GenAI roles.

3.1 The agent loop

Most agent frameworks implement some version of Observe → Think → Act: the agent reads the current state (user goal + tool results so far), decides on a next step (possibly calling a tool), executes it, and loops until it decides the goal is satisfied.

Analogy
An agent is like a new employee with a notebook (context/memory) and a company phone loaded with apps (tools): email, calendar, database. Given a goal, they check their notes, decide which app to use next, act, write down the result, and repeat — checking in with a manager (guardrails) before anything risky.

3.2 Tool calling & memory

Tool/function calling lets the model emit a structured request (e.g. get_weather(city)) which your application executes and feeds the result back in. Short-term memory is just the conversation/context window; long-term memory typically lives in a vector store or database the agent can query across sessions.

ReAct vs Plan-and-Execute

PatternHow it worksBest for
ReActInterleaves reasoning and single actions, one step at a timeExploratory tasks where each result changes the next step
Plan-and-ExecuteProduces a full multi-step plan upfront, then executes it (with re-planning on failure)Well-scoped tasks where the whole path can be foreseen

Single-agent vs multi-agent

Single agentMulti-agent
ComplexityLower to build & debugHigher — needs orchestration & message protocols
Good forFocused, bounded tasksTasks needing specialized roles (researcher, coder, reviewer)
Failure modeGets stuck aloneAgents can loop, disagree, or duplicate work
Trace the agent

Goal: "Book the cheapest flight to Delhi next Friday." The agent has just called search_flights() and gotten 12 results. What should it do next?

Common misconception
"Agents are fully autonomous and need no supervision." Production agents typically need guardrails — approval steps, spending limits, sandboxing — because LLMs can still misinterpret goals or loop on a bad plan.
Common misconception
"More tools always make an agent better." Too many overlapping tools increase decision confusion and error rate; tool sets should be curated and well-documented, not maximized.
Key takeaways
  • The agent loop is Observe → Think → Act, repeated until the goal is met
  • Tool calling is structured function invocation the app executes on the model's behalf
  • ReAct suits step-by-step exploration; Plan-and-Execute suits foreseeable multi-step tasks
  • Multi-agent systems add orchestration complexity in exchange for role specialization
  • Guardrails (approval, limits, sandboxing) are essential, not optional, in production agents

Module 4 · Mastery

System Design, Evaluation & Behavioral Rounds

Senior GenAI interviews test whether you can architect a full system, reason about cost/latency/safety tradeoffs, and narrate your own experience convincingly.

4.1 Designing a GenAI system end-to-end

Case study: "Design an AI customer support agent for an e-commerce company." A strong answer moves through: intake/gateway → orchestrator (routes to RAG vs tools vs escalation) → retrieval layer over product/policy docs → LLM generation → safety filter → response, with logging/monitoring wrapping the whole pipeline.

Analogy
Designing a GenAI system is like designing a restaurant kitchen: prep work (embedding & indexing documents) happens ahead of time, cooking (inference) happens per order, and a quality-control pass (evaluation, safety filters) checks every dish before it reaches the customer.

4.2 Evaluation, safety & scaling

Evaluation

Combine automatic metrics (exact match, ROUGE/BLEU where applicable), LLM-as-judge scoring for open-ended quality, and periodic human review — no single metric is sufficient alone.

Safety & alignment

RLHF (reinforcement learning from human feedback) shapes model behavior toward helpfulness and safety; production systems layer additional guardrails, content filters, and red-teaming on top.

Latency & cost

Levers include response caching, request batching, smaller distilled models for simple sub-tasks, and quantization to shrink model size with minimal quality loss.

Behavioral / STAR

Structure project stories as Situation → Task → Action → Result, and be ready to defend one specific technical decision (e.g. "why RAG over fine-tuning here") in depth.

Mini system design pick

A customer asks a question that requires today's live order status. Which component should the orchestrator route to?

Common misconception
"System design interviews only care about the model." Interviewers weigh data flow, latency/cost tradeoffs, evaluation, and failure handling at least as heavily as model choice.
Common misconception
"Behavioral answers don't matter for a technical role." For GenAI roles especially, being able to narrate a real project's tradeoffs is often how interviewers judge true seniority, not just quiz recall.
Key takeaways
  • A GenAI system is a pipeline: gateway → orchestrator → retrieval/tools → LLM → safety filter
  • Live, per-user data belongs behind a tool call — not RAG or fine-tuning
  • Evaluation should blend automatic metrics, LLM-as-judge, and human review
  • Cost/latency levers: caching, batching, distillation, quantization
  • Use STAR to narrate real project decisions with technical depth
